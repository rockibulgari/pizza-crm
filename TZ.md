# Техническое задание: мини-CRM «Пицца Назрань»

Веб-панель для сотрудников пиццерии. Работает на том же VPS, что и Telegram-бот
(`pizza-bot`), и читает ту же базу заказов `orders.db`.

## 1. Окружение и стек

- Сервер: VPS, Ubuntu 24.04, 1 ГБ RAM. Бот уже работает там как служба systemd.
- Язык: Python 3. Зависимости (`requirements.txt`):
  - `flask` — веб-фреймворк, шаблоны Jinja, хэширование паролей (входит в Flask);
  - `gunicorn` — запуск на сервере;
  - `python-dotenv` — чтение `.env`.
- Больше библиотек нет. Без JS-фреймворков и CSS-фреймворков: чистый HTML, CSS
  и немного JavaScript. Telegram API вызывается встроенным модулем `urllib`,
  база — встроенным `sqlite3`.
- Vercel, Supabase и другие внешние сервисы не используются.

## 2. Адрес, HTTPS и запуск на сервере

1. **Адрес панели:** `https://185-168-208-134.sslip.io`.
   - Адрес записан **в одном месте** — первой строкой `Caddyfile` (см. п. 4).
     Код панели адрес не знает и не использует, поэтому переход на свой домен —
     это замена одной строки и перезапуск Caddy.
2. **Caddy** — веб-сервер перед панелью:
   - сам получает и продлевает сертификат Let's Encrypt;
   - с `http://` перенаправляет на `https://`;
   - передаёт запросы в gunicorn на `127.0.0.1:8000`.
3. **gunicorn** запускает панель (встроенный сервер Flask на сервере не используется):
   - слушает только `127.0.0.1:8000`, снаружи напрямую недоступен;
   - 2 воркера (хватает для нескольких сотрудников, укладывается в 1 ГБ).
   - Flask оборачивается в `ProxyFix` (входит в Flask/Werkzeug, доверие одному
     прокси), чтобы панель видела настоящий IP сотрудника и понимала, что запрос
     пришёл по HTTPS.
4. **Файлы для сервера** лежат в папке `deploy/`:
   - `Caddyfile`:
     ```
     185-168-208-134.sslip.io {
         reverse_proxy 127.0.0.1:8000
     }
     ```
   - `pizza-crm.service` — служба systemd для gunicorn. Запускается **от того же
     пользователя, что и бот**: SQLite в режиме WAL пишет служебные файлы рядом
     с `orders.db`, поэтому нужен доступ на запись к папке бота.
   - `DEPLOY.md` — пошаговая инструкция для новичка: установка Caddy, открытие
     портов 80 и 443 в файрволе (80 нужен Let's Encrypt для проверки и для
     перенаправления), установка зависимостей в venv, запуск служб, создание
     первого админа, проверка.
5. **Запасной вариант.** Если Let's Encrypt не выдаст сертификат для sslip.io
   (например, из-за лимитов на этот общий домен), покупается свой домен
   (например, `crm.<домен>.ru`), его A-запись указывается на IP сервера,
   и в `Caddyfile` меняется одна строка с адресом. Код панели не меняется.

## 3. Настройки (`.env` панели)

Файл `.env` лежит в папке панели и не попадает в git. В репозитории есть
`.env.example` с пустыми значениями и пояснениями.

```
SECRET_KEY=        # длинная случайная строка для подписи сессий; впишет владелец
ORDERS_DB=         # полный путь к orders.db бота
BOT_ENV_FILE=      # полный путь к .env бота — оттуда берётся BOT_TOKEN
```

- `BOT_TOKEN` в `.env` панели **не копируется**: панель читает его из `.env` бота
  по пути `BOT_ENV_FILE`. Так токен хранится в одном месте.
- Если `SECRET_KEY`, `ORDERS_DB` или `BOT_TOKEN` не найдены — панель не запускается
  и пишет в лог понятную ошибку, что именно не задано.
- Владелец вписывает `SECRET_KEY` сам. В `DEPLOY.md` есть команда, как получить
  случайную строку: `python3 -c "import secrets; print(secrets.token_hex(32))"`.

## 4. База данных

1. Панель работает с той же `orders.db`, что и бот. Таблицу `orders` панель
   **не меняет по структуре** — только читает её и обновляет поле `status`.
   Бот не меняется вообще.
2. Свои таблицы панель создаёт при запуске в той же базе, если их ещё нет:

   | Таблица          | Что хранится                                                       |
   |------------------|--------------------------------------------------------------------|
   | `staff`          | сотрудники: `id`, `login` (уникальный), `name`, `password_hash`, `role` («admin»/«operator»), `active`, `created_at` |
   | `status_log`     | история: `id`, `order_id`, `staff_id`, `old_status`, `new_status`, `changed_at` (по Москве), `notified` (дошло ли сообщение клиенту) |
   | `login_attempts` | неудачные попытки входа: `ip`, `login`, `attempted_at`             |

3. **Совместная работа с ботом.** Бот и панель пишут в одну базу одновременно:
   - при запуске панель один раз включает режим `PRAGMA journal_mode = WAL`
     (он сохраняется в файле базы и действует и для бота);
   - каждое соединение панели ставит `PRAGMA busy_timeout = 5000` — при занятой
     базе подождать до 5 секунд, а не падать с ошибкой.
4. **Время.** Всё время — по Москве, в том же формате, что у бота:
   `2026-10-18T15:32:04+03:00`. Дата заказа — первые 10 символов `created_at`.
5. **Поиск по-русски.** Встроенные в SQLite `LOWER` и `LIKE` не понимают регистр
   кириллицы. Для поиска без учёта регистра панель регистрирует в соединении свою
   функцию на Python (`str.lower()`) и ищет через неё.

## 5. Вход и сотрудники

1. **Роли.**
   - **Оператор:** список заказов, карточка заказа, смена статуса.
   - **Админ:** всё то же + статистика + управление сотрудниками.
   - Страницы админа для оператора недоступны (ответ 403 и сообщение
     «Недостаточно прав»), в меню их у оператора нет.
2. **Первый админ** создаётся командой на сервере:
   `flask --app app create-admin` — команда спрашивает логин, имя и пароль.
3. **Управление сотрудниками (админ):**
   - добавить сотрудника: логин, имя, роль, пароль;
   - сменить пароль сотруднику, сменить роль;
   - отключить / включить сотрудника. Отключённый не может войти, а если уже вошёл —
     его выкидывает на страницу входа при следующем действии.
   - Сотрудники не удаляются (на них ссылается история статусов), только отключаются.
   - Админ не может отключить сам себя и снять с себя роль админа — чтобы не
     остаться без единого админа.
   - Пароль — не короче 8 символов. Хранится только хэш (`werkzeug.security`).
4. **Сессия:** после входа сотрудник остаётся в системе 12 часов (смена), потом
   вход заново. Кнопка «Выйти» есть на каждой странице.

## 6. Безопасность

1. **Защита от подбора пароля.**
   - Неудачные попытки записываются в `login_attempts` (в базу, а не в память:
     у gunicorn несколько воркеров, память у них не общая).
   - Если с одного IP **или** для одного логина было **5 неудачных попыток
     за последние 5 минут** — вход с этого IP / в этот логин блокируется
     на **5 минут** с момента последней неудачной попытки. Показывается:
     «Слишком много попыток. Попробуйте через N мин.»
   - Во время блокировки пароль не проверяется, даже правильный.
   - После успешного входа неудачные попытки для этого логина и IP стираются.
   - Сообщение об ошибке входа одно на все случаи: «Неверный логин или пароль»
     (не подсказываем, существует ли логин).
   - Записи старше суток удаляются при очередной попытке входа.
2. **Защита от CSRF.**
   - При входе в сессию кладётся случайный CSRF-токен (`secrets.token_urlsafe`).
   - Каждая форма с методом POST (включая форму входа) содержит скрытое поле
     с токеном; запросы из JavaScript передают его в заголовке `X-CSRF-Token`.
   - Перед обработкой любого POST панель сверяет токен
     (`hmac.compare_digest`). Нет или не совпадает — ответ 400
     «Форма устарела, обновите страницу».
   - Всё, что меняет данные, делается только через POST. GET-запросы ничего
     не меняют.
   - Реализуется своими силами (несколько строк), без Flask-WTF.
3. **Cookie сессии:**
   - `SESSION_COOKIE_SECURE = True` — cookie передаётся только по HTTPS;
   - `SESSION_COOKIE_HTTPONLY = True` — недоступна из JavaScript;
   - `SESSION_COOKIE_SAMESITE = "Lax"`.
   - Сессия подписана `SECRET_KEY` из `.env`.
   - Для локальной проверки на своём компьютере используется `http://localhost`:
     Chrome и Firefox принимают такие cookie на localhost и без HTTPS.
4. **Прочее.**
   - Все данные в шаблонах экранируются (Jinja делает это по умолчанию,
     `|safe` для данных из базы не используется).
   - Все SQL-запросы — с параметрами `?`, без подстановки строк.
   - `.env`, `orders.db*` — в `.gitignore`.

## 7. Список заказов

1. **Главная страница** после входа — список заказов, новые сверху.
2. **Строка заказа:** номер, дата и время (сегодня — только время, иначе
   «17.10 21:05»), имя клиента, телефон, сумма, статус со смайлом.
   Статусы выделены цветом.
3. **Фильтр по статусу** — кнопки-вкладки:
   «Активные» (новый, принят, готовится, в пути) — открыта по умолчанию,
   «Все», и по одной на каждый статус: новый, принят, готовится, в пути,
   доставлен, отменён. На вкладках — количество заказов.
4. **Поиск** — одно поле: по номеру заказа, имени, телефону, адресу.
   - Без учёта регистра (см. раздел 4, п. 5).
   - В телефоне сравниваются только цифры: «8 928 123» найдёт «+7 (928) 123-45-67»
     по совпадению «928123».
   - Поиск работает вместе с фильтром по статусу.
5. **Страницы:** по 50 заказов, кнопки «◀ Назад» / «Вперёд ▶».
   Фильтр, поиск и страница хранятся в адресе (`?status=…&q=…&page=…`),
   чтобы обновление страницы ничего не сбрасывало.
6. **Вёрстка:** на компьютере — таблица, на телефоне (ширина экрана меньше
   ~700 px) — карточки друг под другом. Делается медиазапросами CSS.

## 8. Карточка заказа и смена статуса

1. **Карточка** (отдельная страница по клику на заказ): номер, дата и время,
   позиции (название, размер, количество, цена, сумма строки), сумма без скидки,
   скидка, итог, имя, телефон (ссылка `tel:` — на телефоне сразу звонок), адрес,
   комментарий, способ оплаты, ссылка на клиента в Telegram (`tg://user?id=…`),
   текущий статус.
2. **Кнопки статусов** — как в боте: «✅ Принят», «🍕 Готовится», «🚗 В пути»,
   «✔️ Доставлен», «❌ Отменён». Текущий статус подсвечен. На телефоне кнопки
   крупные, во всю ширину.
   - Статус меняется свободно, в любом порядке (как в боте).
   - Вернуть статус «новый» нельзя (в боте тоже нет такой кнопки).
   - Перед «❌ Отменён» — подтверждение «Отменить заказ №N?».
3. **Что происходит при смене статуса:**
   1. В базе обновляется `status` у заказа, в `status_log` пишется запись
      (кто, когда, с чего на что).
   2. Клиенту в Telegram уходит сообщение **тем же текстом, что присылает бот**,
      например «Ваш заказ №7 в пути 🚗». Точные тексты для всех статусов берутся
      из `bot.py` при разработке, чтобы клиент не видел разницы.
      Отправка — запрос к `https://api.telegram.org/bot<TOKEN>/sendMessage`
      через `urllib`, таймаут 10 секунд.
   3. Сотруднику показывается результат:
      - «Статус изменён, клиент уведомлён»;
      - если Telegram не ответил или клиент заблокировал бота — статус всё равно
        сохранён, показывается «Статус изменён, но клиенту сообщение не доставлено»
        (в `status_log.notified` пишется 0);
      - если статус уже такой — «Статус уже такой», в базу ничего не пишется,
        клиенту ничего не уходит;
      - если запись в базу не удалась — «Не удалось сменить статус, попробуйте
        ещё раз», клиенту ничего не уходит.
4. **История статусов** — внизу карточки: «18:42 · Айша · принят → готовится ·
   клиент уведомлён». Смены статуса через бота сюда не попадают (бот не меняется) —
   под историей мелкая подпись об этом.
5. **Совместимость с ботом.** Админ по-прежнему может менять статусы кнопками
   в Telegram. Ограничение, о котором известно: строка «Статус: …» в уведомлении
   админу в Telegram после смены статуса из панели не обновится. Актуальный
   статус всегда — в панели и в базе.

## 9. Автообновление и звук

1. Пока открыт список заказов, страница раз в **15 секунд** запрашивает у панели
   свежий список (тот же фильтр, поиск и страницу) и подменяет таблицу без
   перезагрузки страницы. Поле поиска при этом не сбрасывается.
2. Если появился заказ с номером больше, чем был, — играет короткий звук,
   а новые строки подсвечиваются на 30 секунд. В заголовке вкладки браузера —
   «(N) Новые заказы».
3. Браузер не даёт сайту играть звук, пока по странице ни разу не кликнули.
   Поэтому вверху есть кнопка «🔔 Включить звук»; после нажатия она меняется
   на «🔔 Звук включён». Выбор запоминается в браузере (`localStorage`).
4. Звук генерируется в браузере (Web Audio API), отдельный аудиофайл не нужен.
5. Если сервер недоступен — вверху появляется полоска «Нет связи с сервером»,
   попытки продолжаются; при восстановлении полоска исчезает.

## 10. Статистика (только админ)

1. **Период:** кнопки «Сегодня», «7 дней», «30 дней» и поля «с … по …» для своих дат.
   По умолчанию — 7 дней. Даты — по Москве.
2. **Итоги за период:** заказов всего, выручка, средний чек, отменённых заказов.
   - **Отменённые входят в количество заказов, но не в выручку и не в средний чек**
     (как в команде `/today` бота).
   - Средний чек = выручка / число неотменённых заказов.
3. **По дням** — таблица: дата, заказов, выручка, средний чек, отменено.
   Дни без заказов показываются нулями (чтобы не было «дыр»).
4. **График выручки по дням** — столбики на чистом HTML/CSS (высота столбика
   в процентах от максимального дня), под столбиком дата, при наведении/нажатии —
   сумма. На телефоне график прокручивается вбок, если дней много.
5. **Популярные пиццы** — таблица по убыванию проданных штук:
   пицца, штук всего, из них 30 см, из них 40 см, выручка.
   - Считается по позициям из поля `items` (JSON) неотменённых заказов
     (SQLite-функция `json_each` или разбор в Python).
   - Выручка по пицце считается **по ценам до скидки** — скидка в базе хранится
     на весь заказ, а не на позицию. Под таблицей подпись: «Выручка по пиццам —
     без учёта скидки 15%».

## 12. Не входит в эту версию

- Изменения в боте.
- Редактирование содержимого заказа (позиции, адрес, суммы).
- Создание заказов из панели.
- Выгрузка в Excel, печать чеков, бэкапы базы.
